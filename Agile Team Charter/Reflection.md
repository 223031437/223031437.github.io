## Introduction

Writing the Agile Team Charter for the **SQL Server Health Monitoring Dashboard** project was an important step in preparing for the project and establishing a clear direction for the work ahead. The charter helped me understand what needed to be achieved, how the project would be managed, and what responsibilities and expectations needed to be established before development began.

Since the project involved learning **SQL Server Database Administration**, developing **T-SQL scripts**, monitoring database performance, and building a functional dashboard within a seven-week timeline, having a clear plan was essential.

## Establishing Project Purpose and Vision

Before the project began, the Team Charter helped establish a shared understanding of the project's purpose and vision. It defined the primary objective as developing a dashboard capable of monitoring:

- Failed SQL Agent Jobs
- Backup Status
- Database Growth
- Blocking Sessions
- Query Execution Performance
- Resource Utilisation
- Wait Statistics
- General SQL Server Health Indicators

Defining these objectives early helped me identify the skills I needed to develop and the deliverables I needed to complete. It also helped establish realistic expectations about the project, considering the limited timeline, available resources, and the need to learn new technical concepts while developing the solution.

## Supporting Project Execution

During the project, the charter served as a reference point for organising tasks, monitoring progress, and maintaining focus on the intended outcomes.

By establishing **Kanban using Trello** as the workflow management approach, together with:

- Daily Progress Reviews
- Weekly Backlog Refinement
- Sprint Planning
- Sprint Reviews
- Sprint Retrospectives

the charter provided a structured framework for managing the work.

It encouraged me to review progress regularly, identify blockers early, and make adjustments whenever challenges arose. The working agreements reinforced the importance of:

- Testing scripts before implementation
- Documenting learning activities
- Following SQL Server best practices
- Maintaining version control for project artefacts

These agreements helped me approach the project more systematically and understand that successful project delivery involves more than simply completing technical tasks.

# Structure of the Team Charter and Key Information

The Team Charter was divided into eleven sections, each focusing on a specific aspect of project organisation and collaboration.

## 1. Team Purpose and Vision

This section explained the project's mission, defined what success would look like, and identified the dashboard's core monitoring features. It helped establish clear objectives from the beginning of the project.

## 2. Team Members and Roles

This section outlined the responsibilities of the various project roles, including:

- Product Owner / DBA Learner
- Scrum Master
- SQL Developer
- Database Administrator
- Tester

This helped clarify the responsibilities required to complete the project successfully.

## 3. Ways of Working

This section identified **Kanban using Trello** as the chosen project management methodology and specified the frequency of:

- Progress Reviews
- Backlog Refinement Sessions
- Sprint Planning
- Sprint Reviews
- Sprint Retrospectives

## 4. Working Agreements

This section defined expectations relating to:

- Punctuality
- Constructive Feedback
- Early Communication of Blockers
- Continuous Improvement
- Script Testing
- Documentation
- Version Control

These agreements helped create a professional and organized working environment.

## 5. Communication

This section identified the primary communication channels used throughout the project:

- Email
- Trello
- Microsoft Teams

It also established expectations regarding:

- Daily Task Reviews
- Urgent Issue Communication
- Sharing Meeting Notes and Decisions

## 6. Decision-Making

This section explained that decisions would be made through consensus wherever possible, while the Product Owner would have the final decision when necessary. This provided a practical approach for resolving disagreements and maintaining project momentum.

## 7. Definition of Done

This section established the conditions required before work could be considered complete:

- Successful Script Execution
- Validated Test Results
- Verified Dashboard Functionality
- Updated Documentation
- Product Owner Approval
- Source Control Updates
- Recording Lessons Learned in the Project Logbook

The Definition of Done ensured quality standards were consistently maintained throughout the project.

## 8. Core Values and Behaviours

This section identified the key values that guided the project:

- Respect
- Transparency
- Accountability
- Trust
- Continuous Learning

These values encouraged positive collaboration and professional behaviour.

## 9. Risks and Constraints

This section identified potential project challenges, including:

- Limited Dashboard Development Experience
- SQL Server Performance Monitoring Complexity
- Query Optimisation Difficulties
- Data Availability Challenges

It also documented project constraints and dependencies, including:

- SQL Server
- SQL Server Management Studio (SSMS)
- Spring Boot Backend
- Dashboard Frontend
- Seven-Week Project Timeline
- Limited Resources

## 10. Review and Improvement

This section stated that the charter should be reviewed and updated whenever necessary to ensure it remained relevant throughout the project lifecycle.

## 11. Team Commitment

This final section documented the commitment to:

- Agile Principles
- Continuous Learning
- High-Quality Solutions
- Open Communication
- Meeting Project Objectives
- Satisfying Stakeholder Expectations

# How the Team Charter Benefited Me

One of the main benefits of writing the Team Charter was that it encouraged me to think about the project before focusing on the technical implementation.

Instead of immediately concentrating on writing SQL scripts or building dashboard components, I had to consider:

- Project Objectives
- Available Resources
- Team Responsibilities
- Project Risks
- Communication Methods
- Quality Expectations

This broader perspective helped me understand the importance of project planning and preparation.

### Early Risk Identification

The charter also helped me recognise the importance of identifying risks early.

For example, limited experience with SQL Server performance monitoring could increase the time required for development and testing. By acknowledging this risk from the beginning, I better understood the importance of:

- Continuous Learning
- Frequent Testing
- Proper Documentation
- Regular Progress Reviews

### Understanding Quality Through the Definition of Done

Another significant benefit was establishing a clear **Definition of Done**.

This helped me understand that completing a task does not automatically mean it is ready for delivery. Work must also be:

- Tested
- Validated
- Documented
- Approved

This encouraged a more disciplined approach to quality assurance and accountability.

### Supporting Continuous Improvement

The charter also supported continuous improvement through the inclusion of retrospectives and the requirement to document lessons learned within the Agile Logbook.

This created opportunities to:

- Reflect on Successful Practices
- Identify Project Challenges
- Improve Future Processes
- Develop Better Working Habits

These activities contributed to personal growth and helped improve the overall project outcome.

## Conclusion

Overall, writing the Agile Team Charter was valuable both before and during the development of the **SQL Server Health Monitoring Dashboard** project.

Before development began, it established the project's purpose, objectives, responsibilities, working arrangements, and expectations. During the project, it provided a reference framework for managing tasks, communicating effectively, identifying and addressing risks, maintaining quality standards, and evaluating progress.

The experience taught me that a Team Charter is not simply a document created to satisfy a project requirement. Instead, it is a practical guide that helps establish direction, accountability, and a shared understanding of how work should be carried out.

I also learned that effective project management begins before development starts and continues throughout planning, execution, monitoring, and continuous improvement. As a result, the Team Charter helped me approach the project with greater structure, improved organisation, and a clearer understanding of what was required to deliver a successful solution.
