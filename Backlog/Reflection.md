## Introduction

As a DBA intern, my primary objective was to bridge the gap between theoretical database knowledge and real-world administration while also delivering tangible value to the team. To achieve this, I undertook the development of a **SQL Server Health Dashboard**.

This project required more than simply learning SQL Server concepts. It involved applying Agile principles to define requirements, break down work into manageable tasks, track progress, and deliver a functional solution. The process of creating User Stories, identifying actionable tasks, and organizing them into a Product Backlog helped me understand both database administration and modern software development practices.

---

# Part 1: Process of Creating User Stories and Defining Tasks

In my work environment, I could not simply state that I wanted to learn SQL Server. Instead, I needed a structured and measurable approach to demonstrate progress and value to the team.

Working with my senior DBA mentor, I defined a series of **User Stories** that described the functionality required by stakeholders and the learning outcomes I needed to achieve. These User Stories represented the **"what"** and **"why"** of the project.

Once the User Stories were established, I broke them down into smaller, actionable **Tasks**, which represented the **"how"**. This process helped transform high-level goals into practical activities that could be completed, tracked, and evaluated.

The project was divided into five key phases:

## Phase 1: Laying the Foundation (User Stories 1 & 2)

This phase focused on building the foundational knowledge required for the project and understanding SQL Server administration concepts.

Activities included:

- Learning SQL and T-SQL fundamentals
- Exploring database administration concepts
- Understanding backup and recovery strategies
- Learning performance monitoring techniques
- Investigating SQL Server best practices
- Researching monitoring requirements for the dashboard

The goal of this phase was to establish the technical knowledge required before beginning development.

## Phase 2: Shifting to Proactive Monitoring (User Story 3)

The focus of this phase was understanding how to proactively monitor SQL Server environments rather than simply reacting to issues after they occurred.

Tasks included:

- Investigating failed SQL Agent jobs
- Monitoring backup status and database growth
- Analyzing blocking sessions
- Studying wait statistics
- Reviewing query performance metrics
- Identifying important health indicators

This phase helped me understand which database metrics provide meaningful insights into SQL Server health and performance.

## Phase 3: Architecting the Solution (User Story 4)

Once the monitoring requirements were identified, I moved on to designing the overall solution architecture.

Tasks included:

- Defining the dashboard architecture
- Designing backend components
- Designing REST API endpoints
- Planning database monitoring scripts
- Determining frontend requirements
- Defining data flow between system components

This phase ensured that development activities followed a structured plan rather than being implemented without design considerations.

## Phase 4: Full-Stack Development (User Stories 5 & 6)

This phase focused on implementing the solution.

Activities included:

### Backend Development

- Creating Spring Boot project structure
- Developing REST API endpoints
- Implementing monitoring services
- Developing SQL data collection scripts
- Configuring database connectivity
- Implementing exception handling

### Frontend Development

- Creating dashboard user interface
- Designing dashboard widgets
- Implementing API integration
- Displaying health metrics
- Visualizing monitoring data
- Improving dashboard usability

This phase transformed the initial design into a functional monitoring application.

## Phase 5: Validation and Professional Wrap-Up (User Story 7)

The final phase focused on ensuring quality and completing project deliverables.

Tasks included:

- Testing dashboard functionality
- Validating monitoring results
- Fixing defects and bugs
- Optimizing performance
- Updating project documentation
- Completing Agile project artefacts
- Reviewing lessons learned
- Preparing final project deliverables

This phase ensured that the dashboard met quality standards and project requirements before completion.

# Part 2: How the Product Backlog Was Created

After defining the detailed tasks for each User Story, I needed a structured way to track progress using Agile practices.

My team used a Taskboard, which required converting the detailed task list into a formal **Product Backlog**.

The following methodology was used.

## 1. Thematic Grouping

The first step was grouping related tasks into logical categories. Similar tasks were organized together to create larger bodies of work.

Examples included:

- Learning and Research
- SQL Monitoring Development
- Backend Development
- Frontend Development
- Testing and Validation
- Documentation

This made the backlog easier to manage and understand.

## 2. Mapping Tasks to User Story Epics

Each set of tasks was then linked to its corresponding User Story.

This ensured that every task contributed directly to a project objective and made progress tracking more transparent.

The User Stories effectively became project epics that grouped related activities together.

## 3. Prioritization by Dependency

Tasks were prioritized based on their dependencies.

For example:

- SQL Server fundamentals needed to be learned before developing monitoring scripts.
- Monitoring scripts needed to exist before API endpoints could expose the data.
- Backend services needed to be completed before dashboard integration could occur.
- Testing could only occur once development was complete.

This dependency-driven approach helped ensure that work progressed in a logical sequence.

## 4. Structuring the Taskboard

Finally, the backlog was organized into a Taskboard to support Agile workflow management.

Tasks moved through workflow stages such as:

- To Do
- In Progress
- Testing
- Completed

This provided visibility into project progress and helped identify bottlenecks or blocked work items.
